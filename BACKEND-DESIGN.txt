FRESHCART — BACKEND DESIGN  (v2)
Multi-tenant grocery-delivery SaaS
Node.js · Express · MongoDB (Mongoose)
================================================================================
Revision 2, 13 August 2026. Supersedes v1 (single-tenant).
Design only. No implementation yet.

WHAT CHANGED FROM v1
  v1 designed one supermarket with two clients. This is a MULTI-TENANT SaaS:
  many supermarkets ("tenants"), each with their own customers, catalogue,
  staff and branding, on one shared server and one shared database.

  That single change touches every collection, every query and every route.
  It is the reason section 1 comes before the data model.

ONE SERVER, FOUR CLIENTS
  1. Customer app        React Native (Expo)   — public API
  2. Store admin CMS     PWA                   — /admin
  3. Delivery staff app  PWA                   — /delivery      (not built yet)
  4. Super admin portal  Web                   — /platform      (not built yet)

  Clients 3 and 4 do not exist. Their endpoints are specified here and built
  server-side, so the frontends have something to be written against.

SOURCE OF TRUTH
  Schemas derive from the app's real type layer, src/data/types.ts, and the
  module scope in CMS-SCOPE.txt. Field names match the app unless a DEPARTURE
  says otherwise. Where this document departs, it says so and gives a reason.

0. DECISIONS SETTLED  (locked — do not relitigate without changing this doc)
================================================================================

  D1  Multi-tenancy         Shared DB, shared collections, `tenantId` on every
                            tenant-scoped document. Enforced by middleware.
  D2  Tenant per business   One supermarket = one tenant = ONE location.
                            No branches. No per-branch stock or pricing.
  D3  Bilingual format      Nested `{ en, ar }` (Localized), NOT name_en/name_ar.
  D4  Category browsing     KEPT. The app's Categories tab and Category listing
                            screen stay. Categories are a browse surface, not
                            just a filter.
  D5  Fulfillment types     `delivery` | `curbside`. Two options only.
  D6  Delivery slots        DROPPED. No scheduling. Delivery is ASAP.
  D7  Credit balance        Running balance. balance = sum of ALL ledger entries
                            (charges positive, payments negative). Each entry
                            stores `balanceAfter`.
  D8  Stock                 Three-state flag (available|low|out). Never a count.
                            Never decremented. Oversell is accepted — see §9.
  D9  Error envelope        { error: { code, message, details } }
  D10 Identifiers           MongoDB ObjectId, exposed as string `id`.
  D11 Endpoint shapes       The backend defines them. Clients adapt.
  D12 Payment gateway       v2. v1 records a payment method and takes no money.
  D13 Push notifications    Expo Push (wraps APNs + FCM). Not FCM direct.
  D14 Tenant billing        Real invoicing. Collection payment is manual in v1
                            (follows from D12).
  D15 Promos / banners /    All three SURVIVE. They exist in the app and in
      curbside car details  CMS-SCOPE modules 07, 08, 09.

ASSUMPTIONS I MADE — correct me if wrong
  A1  Each supermarket ships its OWN app build (white-label). The tenant is
      baked into app config, not chosen by the customer at runtime. See §2.
      This follows from "existing supermarkets bring their existing customers".
  A2  A customer belongs to exactly one tenant. The same phone number at two
      supermarkets is two separate customer records.
  A3  `curbside` replaces `pickup` on the wire. The app currently says
      `pickup`; this is a small app-side rename. Status names inside the
      curbside chain keep the app's existing spelling.


================================================================================
1. MULTI-TENANCY — THE FOUNDATION
================================================================================
Build this first. Everything else depends on it, and a leak here is the
worst bug this system can have: one supermarket reading another's customers.

1.1  THE RULE
     Every tenant-scoped collection carries `tenantId: ObjectId, indexed`.
     Every tenant-scoped query filters on it.
     No route handler is trusted to remember. It is structural.

1.2  HOW A TENANT IS RESOLVED
     Resolution order, first match wins:

       1. Authenticated request → `tenantId` claim inside the JWT.
       2. Public/unauthenticated request → `X-Tenant-Id` header, sent by
          every client build.
       3. Super admin acting cross-tenant → explicit `?tenantId=` query
          param, allowed ONLY for role `superAdmin`.

     RULE: if a JWT carries a tenantId AND a header is present and they
     disagree, reject with 403 TENANT_MISMATCH. Never let the header win
     over the token.

1.3  HOW ISOLATION IS ENFORCED
     Two layers, because one is not enough.

     Layer 1 — request context
       An AsyncLocalStorage store holds { tenantId, userId, role, requestId }
       for the life of the request, set by `tenantContext` middleware before
       any handler runs.

     Layer 2 — Mongoose plugin  ← the important one
       A global plugin applied to every tenant-scoped schema:
         - pre-hook on find, findOne, findOneAndUpdate, count, aggregate,
           updateMany, deleteMany, distinct: inject `tenantId` from context
           if not already present.
         - pre-validate on save: stamp `tenantId` from context.
         - if context has no tenantId and the role is not superAdmin, THROW.
           A missing tenant is a bug, not a wildcard.

     RULE: the plugin fails closed. An un-scoped query on a tenant-scoped
     collection is an exception, never a full-collection scan.

     NOTE ON AGGREGATIONS: the plugin injects a `$match` stage at position 0.
     Any aggregation written by hand must not assume it is first. This is the
     most likely place isolation silently breaks — cover it in tests.

1.4  WHAT IS **NOT** TENANT-SCOPED
     tenants, platformUsers (super admins), plans, invoices, iconCatalog,
     and the platform-level audit log. Everything else is scoped.

1.5  COMPOUND INDEX RULE
     `tenantId` is the FIRST key of every index on a tenant-scoped
     collection. An index that does not lead with tenantId will not be used
     by the scoped query and is dead weight. This is repeated in §12 and it
     is not optional.

1.6  TESTING THE BOUNDARY
     A dedicated suite seeds two tenants with identical-looking data and
     asserts every list, get, update and delete endpoint returns or touches
     only tenant A's rows when called with tenant A's token. New endpoints
     do not merge without a row in that suite.

2. STACK, CONVENTIONS AND TOPOLOGY
================================================================================

  Runtime        Node 20 LTS
  Framework      Express 4
  Database       MongoDB 7, Mongoose 8 — REPLICA SET REQUIRED (see below)
  Validation     Zod at every route boundary, before the handler runs
  Auth           JWT access token (60 min) + rotating refresh token (60 days)
  Passwords      argon2. Staff/admin only — customers never have one.
  Realtime       Socket.io, namespaced per tenant (§14)
  Push           Expo Push (§15)
  Files          Presigned direct-to-storage upload, S3-compatible (§16)
  Jobs           BullMQ + Redis — Excel import, rider timeouts, rollups,
                 invoice generation
  Logging        pino, requestId + tenantId on every line
  Testing        vitest + mongodb-memory-server (replica-set mode)

TOPOLOGY — READ THIS BEFORE INSTALLING MONGO
  This design uses multi-document transactions in six places (§13). MongoDB
  cannot run a transaction on a standalone `mongod`, which is the default
  local install. Dev must run a single-node REPLICA SET (trivial via Docker);
  prod runs Atlas or a 3-node set. mongodb-memory-server must be started in
  replica-set mode or every transaction test fails.

API VERSIONING
  All routes under `/api/v1`. The app's existing base URL is
  `http://localhost:4000/api` — it gains the `/v1` segment. Decided now
  because adding it later breaks every deployed build.

CONVENTIONS
  - Every response is JSON. Errors share one shape (§11).
  - Every collection stores createdAt / updatedAt (Mongoose timestamps).
  - Documents expose `id` (string). `_id`, `__v` and `tenantId` are stripped
    in toJSON. Clients never see tenantId — they cannot influence it anyway.
  - Soft delete via `archivedAt` on catalogue documents. Orders, ledger
    entries and invoices are never deleted.
  - Money is an integer count of fils (§10).
  - All timestamps stored UTC. All date-boundary logic uses the tenant's
    timezone, default `Asia/Dubai` (§17).
  - Lists paginate. Admin tables use offset (`?page=&limit=`) and return
    `total`. Order queues and ledgers use cursor (`?cursor=&limit=`) and
    return `nextCursor` — see §12.

SHARED SUBDOCUMENT — Localized
--------------------------------------------------------------------------------
  { en: String, ar: String }

  Used by: category and subcategory names, product names/subtitles/
  descriptions/shelf, variant axis and option names, address label/lines,
  payment titles, order line name/variantLabel, rider name, credit entry
  title/subtitle, car colour, legal copy, tenant display name.

  required. The app has no fallback path — a missing `ar` renders an empty
  string to an Arabic customer.

  can land rows before translation. Public endpoints NEVER return drafts.

  `name_ar`. Overruled by D3 — the app reads nested `{en, ar}` everywhere and
  changing it would touch every screen. Note that the comment in the app's
  api/client.ts ("the backend returns both name_en and name_ar") is stale and
  should be corrected.

4.14 creditEntries
--------------------------------------------------------------------------------
  accountId       ObjectId -> creditAccounts, indexed
  customerId      ObjectId, indexed
  kind            String, enum: charge | payment
  title           Localized
  subtitle        Localized
  amount          Number (fils)    positive charge, negative payment
  balanceAfter    Number (fils)    running balance immediately after this row
  orderId         ObjectId | null
  recordedBy      ObjectId | null  admin who took the payment; null if system
  at              Date, indexed

  RULE (D7): balance = SUM of `amount` across all entries. Charges add,
  payments subtract. `balanceAfter` on the newest entry always equals
  `creditAccounts.balance`. The ledger is APPEND-ONLY — a mistake is
  corrected with a compensating entry, never an edit or a delete.

  DEPARTURE: v1 had a `settled: Boolean` per entry and computed the balance
  from unsettled rows only. Dropped — it produced a balance of 203.50 on the
  seed fixture where a straight sum gives 3.50, and it required a payment
  allocation algorithm nobody specified. The running balance is simpler,
  auditable and matches the build prompt's `balanceAfter`.

  SEED CONSEQUENCE: the app's CREDIT_ACCOUNT fixture in src/data/orders.ts
  must be corrected during seeding — its stated balance does not equal the
  sum of its entries. The seed assertion in §21 will catch this.

  APP CONSEQUENCE: `CreditEntry.settled` is removed from the app's type. The
  My Credit screen's settled badge is derived instead: an entry is shown as
  settled when `balanceAfter <= 0`.

  INDEX { tenantId: 1, accountId: 1, at: -1 }

  is the MINIMUM grade, not an exact match.

5.3  CUSTOMER AUTH — PHONE + OTP
  POST /auth/otp     { phone, channel }        → { challengeId, expiresIn }
  POST /auth/verify  { challengeId, code }     → { accessToken, refreshToken,
                                                    user }
  POST /auth/refresh { refreshToken }          → new pair
  POST /auth/logout  { refreshToken }

  - Phone normalised to E.164 on write. UAE default country code.
  - Code is 4 digits (matches the app's 4-box OTP input), argon2-hashed.
  - Challenge expires in 5 minutes; 5 wrong attempts burns it.
  - Resend cooldown 30 seconds — matches the countdown already in LoginScreen.
  - OTP provider is a SWAPPABLE module: `OtpProvider` interface with
    `send(phone, code, channel)`. Ship a console provider for dev, one SMS and
    one WhatsApp provider for prod. Credentials may be per-tenant.

  ACTION REQUIRED, LONG LEAD TIME: UAE SMS needs a registered sender ID via
  an aggregator; WhatsApp needs a Meta BSP and a pre-approved template.
  Both take weeks. Start the paperwork now — this one-word schema field can
  delay launch more than any code in this document.

  DEPARTURE: `signInWithProvider('google'|'apple')` exists in the app's
  api/auth.ts and AuthContext but LoginScreen renders no buttons for it.
  DROPPED. Social identity yields no verified phone number, and orders,
  credit and rider handoff are all phone-keyed. It is also a trap: shipping
  Google sign-in on iOS makes Apple sign-in mandatory under App Store 4.8.

5.4  STAFF AUTH
  POST /auth/staff/login  { email, password, tenantSlug } → token pair
  POST /auth/platform/login { email, password, totp }     → superAdmin pair

  - argon2id. 10 failed attempts locks the account for 15 minutes.
  - superAdmin login requires TOTP. It can read every tenant's data.

5.5  TOKENS
  Access token   JWT, 60 minutes, claims { sub, role, grade, tenantId, jti }
  Refresh token  opaque 32-byte random, stored hashed, 60 days, ROTATING

  RULE — rotation with reuse detection: every refresh issues a new token and
  marks the old one `replacedBy`. Presenting an already-rotated token means
  it was stolen: revoke the entire `familyId` and force re-authentication.

  DEPARTURE: v1 specified a 15-minute access token. Too aggressive for a
  passwordless app — every expiry that outruns the refresh path dumps a
  customer into an SMS flow while standing in a supermarket aisle on bad
  signal. The security benefit is small: there is no password to protect,
  and rotation is the real control. 60 minutes.

  CLIENT STORAGE: refresh token in Expo SecureStore, access token in memory.
  The app currently keeps a single in-memory token with no refresh path —
  this is an app-side change.

7. MONEY
================================================================================
Store every amount as an INTEGER count of fils. 1 AED = 100 fils.

WHY: the app holds prices as floats — 11, 6.5, 17.25, 4.25 — and patches the
rounding by hand. `Math.round(x * 100) / 100` appears in CheckoutScreen,
CartContext and OrdersContext. That works until a basket accumulates enough
lines for the error to surface in a total a customer disputes.

  AED 11.00  ->  1100
  AED  6.50  ->   650
  AED  4.25  ->   425

The API sends fils. The app divides by 100 at the formatting boundary only,
inside utils/format.ts, which is already the single place money becomes a
string. Nothing else in the app changes.

Currency is AED, fixed. `settings.currency` is a display constant, not a
multi-currency switch — there is no rate table and formatMoney hardcodes both
"AED" and "د.إ".

8. THE PRICING ENGINE
================================================================================
The most important module after tenant isolation, and the fix for the biggest
CRITICAL in CMS-SCOPE §2: today CheckoutScreen computes the total and the
device decides what it pays.

  POST /cart/price
    in   { lines: [{ variantId, quantity }], promoCode?, fulfillment,
           addressId? }
    out  { lines: [{ variantId, quantity, unitPrice, lineTotal,
                     name, variantLabel, icon, stock }],
           subtotal, deliveryFee, discount, total,
           promo: { code, applied, reason? },
           unavailable: [variantId],
           priceToken }

RULES
  1. Prices are read from the database, never accepted from the client.
  2. Out-of-stock variants are returned in `unavailable` and EXCLUDED from
     totals, so the app can show them struck through.
  3. Delivery fee: 0 for curbside, else tenant.settings.deliveryFee.
  4. minOrder is checked here and reported as a reason, not a hard failure —
     the cart must be able to explain itself.
  5. Promo validation runs here and returns a reason on failure.
  6. total = subtotal - discount + deliveryFee, computed in fils.
  7. `priceToken` is a short-lived signed hash of the priced basket. The app
     sends it back to POST /orders.

CART OWNERSHIP: the cart lives on the device. CartContext persists it to
AsyncStorage and joins lines to the catalogue on read. The server stores no
cart and /cart/price is stateless. Consequence, stated so nobody is
surprised: no cross-device cart and no abandoned-cart reporting.

RE-PRICING AT SUBMIT
  POST /orders takes the same shape plus `priceToken` and re-prices
  server-side before writing. It NEVER trusts a client total.
  - If the recomputed total differs from the token → 409 PRICE_CHANGED with
    the corrected basket. The app re-confirms.
  - If a line went out of stock between pricing and submit → 409
    BASKET_CHANGED with the affected variantIds. It is NOT silently dropped:
    charging for a different basket than the customer confirmed is the same
    class of bug as trusting the total.

9. ORDERS
================================================================================

9.1  THE TWO CHAINS
  Both already exist in the app (data/types.ts: DELIVERY_FLOW, PICKUP_FLOW).
  The server owns them.

    delivery:  placed -> packed -> out_for_delivery -> delivered
    curbside:  placed -> packed -> ready_for_pickup -> customer_arrived
                      -> handed_over

  Status spellings inside the curbside chain keep the app's existing names
  (`ready_for_pickup`), even though the fulfillment type is now `curbside`.
  Renaming the statuses too would be churn for nothing.

9.2  RULES
  - Only forward transitions along the order's OWN chain. Anything else is
    409 INVALID_TRANSITION — including a delivery status on a curbside order.
  - `cancelled` is reachable from `placed` or `packed` only.
  - `customer_arrived` is the one transition a CUSTOMER may trigger
    (POST /orders/:id/arrived). Everything else is staff-only.
  - `handed_over` requires `customer_arrived` first. The store cannot hand an
    order to someone who has not said they are there. The app encodes this
    client-side today; it moves here.
  - `delivered` and `handed_over` both require the confirmation code
    (§9.4).
  - Every transition appends to `events` with a timestamp and the acting
    user, emits a Socket.io event (§14) and enqueues a push (§15).

9.3  EVENTS — WHAT IS STORED VS WHAT IS RENDERED
  DEPARTURE: the app's OrderEvent types `at?: string` as "absent for
  milestones that have not happened yet", implying the server pre-populates
  the full chain. It does not. `events` is APPEND-ONLY and contains only what
  actually happened. The app derives future milestones from `flowFor(...)`,
  which already exists client-side. Server truth stays truthful.

9.4  CONFIRMATION CODE AND PROOF OF DELIVERY
  - 4-digit code, server-issued at order creation, cryptographically random.
    CMS-SCOPE §2 flags the current Math.random generation as HIGH: this is
    the number handed over at the door and it is currently guessable.
  - `POST /delivery/orders/:id/confirm` requires the code and captures
    proof: { photoUrl, geo, amountCollected }.
  - amountCollected is mandatory when paymentKind is `cash` and must equal
    the order total, else 409 AMOUNT_MISMATCH.

9.5  AUTOMATIC RIDER ASSIGNMENT
  Runs on creation of a `delivery` order.

  Selection: among users where role=deliveryStaff, status=active,
  availability=available, pick the one with the fewest `activeOrderIds`;
  tie-break on lowest `stats.avgMinutes`.

  Offer and timeout:
    1. Assign, set availability=on_delivery, push to the rider, record
       `assignment.assignedAt` and increment `attempts`.
    2. Enqueue a BullMQ delayed job for ACCEPT_TIMEOUT (default 120s).
    3. If the rider has not accepted when it fires, release them, add them to
       `assignment.lastOfferedTo`, and reassign to the next candidate.
    4. After 3 failed attempts, leave the order unassigned and raise it in
       the CMS queue for manual assignment. Never loop forever.

  RULE: assignment is a transaction (§13.5). Two concurrent orders must not
  both grab the same idle rider.

9.6  OVERSELL AND SUBSTITUTION  — the consequence of D8
  Stock is a manual flag with no quantity, so two customers CAN both buy the
  last unit and nothing can prevent it. There is no POS to read real counts
  from. This is accepted, not solved — but it must be handled at pick time,
  which v1 had no path for.

  At packing, staff may per line:
    - reduce `fulfilledQty` (short pick)
    - mark a line unavailable (`fulfilledQty = 0`)
    - substitute (`substitutedFor` points at the original line)

  On leaving `packed`, the order total is RECOMPUTED from fulfilled
  quantities:
    - card / cash → adjusted total; the difference is refunded or simply not
      collected
    - credit → a compensating creditEntry for the difference, in the same
      transaction
    - the customer receives a push and the receipt shows original vs
      fulfilled

  RULE: the original `lines` are never rewritten. `quantity` is what was
  ordered; `fulfilledQty` is what was picked. The receipt shows both.

9.7  CANCELLATION AND REFUNDS
  - A CUSTOMER may cancel only while status is `placed`.
  - A manager may cancel while `placed` or `packed`.
  - Cancelling a credit order writes a compensating ledger entry in the SAME
    transaction as the status change. The original entry is never touched.
  - Refunds (owner only) are recorded, not executed — there is no gateway
    in v1 (D12). A refund writes an audit row and, for credit orders, a
    ledger entry.

9.8  REFERENCES
  `FC-####`, server-issued, unique per tenant. This format wins because the
  app's fixtures and credit entry titles already use it. The Admin's bare
  numeric ids (`10486`) are display placeholders and adapt.

12. PAGINATION
================================================================================
  Offset  — admin tables where a human wants page numbers.
            `?page=1&limit=20` → { items, page, limit, total }
  Cursor  — customer order list, credit ledger, admin order queue, audit log.

  Cursor encoding: base64 of `{ sortValue, _id }`, always with `_id` as the

13. TRANSACTIONS, CONCURRENCY AND IDEMPOTENCY
================================================================================
Every operation that must be atomic, and why. All require the replica set
(§2). All retry on TransientTransactionError with jittered backoff, max 3.

13.1  ADDRESS PRIMARY SWAP
      Clear the previous primary and set the new one. Without this, a failure
      between the two writes leaves zero or two primaries and the app's
      AddressesContext breaks.

13.2  CREDIT LEDGER APPEND
      Append entry → recompute balance → write balanceAfter → update
      creditAccounts.balance. Reading the balance and writing it back without
      a transaction is exactly the bug CMS-SCOPE §2 calls CRITICAL.
      Also enforces `balance + amount <= limit`, else 409
      CREDIT_LIMIT_EXCEEDED.

13.3  PLACE ORDER  — the big one
      Inside one transaction:
        1. Re-price the basket from the database (§8).
        2. Validate and atomically claim the promo (13.4).
        3. Issue reference and confirmation code.
        4. If paymentKind is credit: append the ledger entry (13.2) and
           check the limit.
        5. Write the order.
      Outside the transaction, after commit: assign rider, emit socket
      events, enqueue pushes. Never do network I/O inside a transaction.

13.4  PROMO CLAIM
      `findOneAndUpdate` with `{ active: true, redemptions: { $lt:
      maxRedemptions } }` in the FILTER and `$inc: { redemptions: 1 }` in the
      update. The filter is the lock. `perCustomerCap` is a counted query on
      promoRedemptions in the same transaction.

      NOTE: the unique index on { promoId, orderId } prevents double-counting
      one order. It does NOT prevent exceeding maxRedemptions under
      concurrency — only the guarded $inc does.

13.5  RIDER ASSIGNMENT
      `findOneAndUpdate` on the chosen rider with
      `{ availability: 'available' }` in the filter. If it returns null,
      someone else took them; pick the next candidate. Prevents two orders
      landing on one idle rider.

13.6  STOCK FLAG TOGGLE
      Not transactional. It is a single field write on one document and there
      is deliberately no quantity to contend on (D8).

13.7  IDEMPOTENCY
      `POST /orders` REQUIRES an `Idempotency-Key` header. Without it, a
      double-tap or a network retry creates two orders, two credit entries
      and two promo redemptions.
        - Key stored with the order (`orders.idempotencyKey`, unique sparse
          per tenant) plus a Redis lock for the in-flight window.
        - A repeat with the same key returns the ORIGINAL order, 200 not 201.
        - TTL 24 hours.
      Also applied to POST /admin/credit/:id/payment and
      POST /delivery/orders/:id/confirm.

14. REALTIME (Socket.io)
================================================================================
  Namespace per tenant: `/t/<tenantId>`. Joining requires a valid JWT whose
  tenantId matches the namespace — the SAME check as HTTP, because a socket
  is an authenticated channel and leaks the same data.

  Rooms
    order:<orderId>     the customer tracking that order
    queue               store admins watching the live order queue
    rider:<userId>      one delivery staff member

  Events (server → client)
    order.created       → queue
    order.status        → queue, order:<id>, rider:<id>
    order.assigned      → queue, rider:<id>
    order.arrived       → queue                     curbside "I'm here"
    order.lines         → queue, order:<id>         short pick / substitution
    rider.location      → order:<id>                 v2, when GPS streams
    stock.changed       → queue

  RULE: sockets carry NOTIFICATIONS, never authority. A client that misses an
  event must reach the same state by re-fetching. Never let a socket payload
  be the only source of a value.

  The app polls today; it moves to sockets with polling as the fallback.

15. NOTIFICATIONS
================================================================================
  Transport: Expo Push (D13). One API that reaches both APNs and iOS/Android
  via FCM underneath. The build prompt said FCM direct — overruled, because
  the customer app is an Expo app and FCM alone does not cover iOS cleanly.
  The delivery staff PWA uses Web Push.

  Tokens live on `users.pushTokens`, registered via POST /me/push-token, and
  are pruned when Expo reports them invalid.

  Triggers
    - every order status transition          → customer
    - order assigned / reassigned            → delivery staff
    - customer arrived                       → store admins
    - short pick or substitution             → customer
    - back-in-stock                          → everyone in notifyRequests
    - credit payment recorded, credit due    → customer
    - invoice issued / overdue               → tenant owner

  RULE: state transitions EMIT A DOMAIN EVENT. A notifier consumes it.
  Nothing in the order module imports the push SDK. This resolves the
  contradiction in v1, where §7 said every transition fires a push while §11
  deferred push entirely.

  All notification copy is Localized and sent in the recipient's `language`.

16. FILE UPLOAD
================================================================================
  v1 deferred this to "later". It cannot be: categories, products, banners,
  tenant logos and delivery proof photos all need it on day one, and seeding
  uploads the bundled category tiles.

  Flow
    1. POST /admin/uploads/sign { contentType, purpose } → { url, fileUrl }
    2. Client PUTs the bytes DIRECTLY to storage.
    3. Client sends `fileUrl` on the create/update call.

  - S3-compatible storage (Cloudflare R2 recommended — free egress).
  - Bytes never pass through Express.
  - Presigned URL valid 5 minutes, single use.
  - Limits: 5 MB, image/jpeg|png|webp only, enforced in the presign
    conditions, not just checked client-side.
  - Path: `<tenantId>/<purpose>/<uuid>.<ext>` — tenant-prefixed so storage
    is auditable and deletable per tenant.
  - Delivery proof photos are PRIVATE: served via short-lived signed GET,
    never a public URL. They contain a customer's doorstep.

17. EXCEL IMPORT
================================================================================
The store admin's primary catalogue tool. There is no POS integration, so
this and the manual stock toggle are the only ways stock and prices change.

  1. UPLOAD      xlsx/csv to storage (§16), create an importBatch.
  2. PARSE       read headers + first 20 rows, return them for mapping.
  3. MAP         admin maps spreadsheet columns → model fields. The map is
                 SAVED on the tenant and offered as the default next time —
                 the same shop uploads the same spreadsheet every week.
  4. VALIDATE    dry run. Produces per-row errors with row and column
                 numbers. Nothing is written.
  5. COMMIT      a background job (BullMQ) writes in batches.

  VARIANT GROUPING: rows sharing a `productKey` (mapped column, or matched by
  name) collapse into one product with many variants. The axis is inferred
  from a mapped attribute column (flavour, size). This is the fiddliest part
  of the module and deserves its own test fixtures.

  CATEGORY CLEANUP: fuzzy-match the category text against existing category
  names in BOTH languages. No confident match → the product lands
  uncategorised with `status: draft` and appears in
  GET /admin/products/needs-fixing. Import never invents categories.

  MATCHING for update-vs-create: barcode first, then (name + variant label).
  Barcode is the only reliable key.

  RULES
    - Import writes DRAFTS. Nothing reaches customers until published.
    - A row that fails validation is skipped and reported; it never aborts
      the batch.
    - Import respects plan limits (§19.2) and fails the batch early if the
      product cap would be exceeded.
    - Every import writes one audit row with the batch stats, not one per
      product.

18. ANALYTICS
================================================================================
Absent entirely from v1, but the Admin's Insights screen already renders best
sellers, category performance, top customers, an orders sparkline and revenue
totals — and the build prompt adds RFM and seasonal flags.

  STRATEGY: precomputed rollups, not live aggregation over `orders`.

  - A nightly job per tenant writes one `dailyRollups` document for the
    previous day, bucketed in the TENANT's timezone.
  - Historical queries read rollups. Fast, and cost is independent of order
    volume.
  - "Today" is the ONLY live aggregation — a small, bounded window.
  - Backfill job to build rollups from existing orders when a tenant onboards
    with history.

  RFM top customers: recency (days since last order), frequency (orders in
  window), monetary (net revenue). Scored 1-5 per axis on tenant-relative
  quintiles, recomputed weekly, cached on a `customerScores` view.

  Seasonal trend flags: compare a product's trailing 4-week units against the
  same weeks last year. Needs a year of data — ship the field, expect it to
  be null until then. Do not fake it.

  Cross-tenant platform analytics (§19) reads the same rollups, summed. This
  is the reason rollups are a collection rather than a cache.

19. PLATFORM / SUPER ADMIN
================================================================================

19.1  TENANT ONBOARDING
  POST /platform/tenants creates the tenant, its owner storeAdmin user, a
  default paymentMethods set, a default merchandising document and the
  seeded car colour list — in ONE transaction. A half-created tenant is
  unusable and nobody will notice until the owner tries to log in.

19.2  PLAN LIMITS
  Enforced at write time, checked in middleware:
    products         blocks create and Excel commit
    ordersPerMonth   soft — warns the owner, never blocks a customer's order
    staffSeats       blocks staff creation

  RULE: never block an ORDER because of a billing limit. Blocking revenue to
  enforce a subscription tier turns a billing problem into a customer-facing
  outage. Warn the owner, invoice the overage.

19.3  BILLING (D14 — real invoicing)
  - Monthly job, per tenant, on the tenant's billing anchor date.
  - Generates an invoice: plan fee + any overage lines, 5% UAE VAT, sequential
    per-year numbering, due 14 days.
  - Status: draft → issued → paid | overdue | void.
  - PAYMENT COLLECTION IS MANUAL IN v1. There is no gateway (D12); an owner
    or super admin marks an invoice paid with a reference. When the gateway
    lands, only the collection step changes — the invoice model does not.
  - Overdue past a grace period flags the tenant for review. Suspension is a
    DELIBERATE human action, never automatic — an automatic suspension takes
    a supermarket offline mid-trading-day.

19.4  SUSPENSION SEMANTICS
  A suspended tenant:
    - customer app → 403 TENANT_SUSPENDED on every route
    - store admin  → read-only, plus the billing screen
    - EXISTING OPEN ORDERS STILL COMPLETE. Orders already placed must reach
      delivery or handover. Never strand a paid basket over a billing dispute.

20. SEARCH AND LOCALISATION
================================================================================

20.1  SEARCH
  DEPARTURE: v1 specified a MongoDB text index over name.en, name.ar,
  subtitle.en, subtitle.ar. Two problems. A text index applies ONE language
  per document, so indexing both languages in one index is already a
  compromise; and Arabic stemming is not part of MongoDB Community's text
  search language set — it belongs to the Enterprise/Atlas feature set, so on
  Community, Arabic degrades to simple tokenisation with no stemming.
  VERIFY THIS against whichever tier you deploy on before relying on it.

  v1 approach instead: a `searchTokens: [String]` array we control.
    - lowercase, strip Arabic diacritics, normalise alef/ya/ta-marbuta
      variants, strip punctuation
    - tokens from name, subtitle and barcode, both languages
    - plain multikey index — predictable, tier-independent, works for prefix
      matching with a regex anchored at ^
  Move to Atlas Search when catalogue size justifies it.

  Every query, including zero-result ones, writes a searchLog. Zero-result
  queries are the cheapest catalogue-gap signal available.

20.2  LANGUAGE
  - `Accept-Language` picks a default but the API RETURNS BOTH languages on
    every Localized field. The app switches without a refetch.
  - Notifications and emails use the recipient's stored `language`.
  - Translation coverage report: rows where `value.ar` is empty. CMS-SCOPE
    module 11 requires a missing Arabic value to be visible BEFORE release.

20.3  TIME
  - All instants stored UTC.
  - Every date boundary — "today's orders", rollup buckets, credit dueDate,
    overdue, opening hours, invoice periods — uses `tenant.locale.timezone`,
    default `Asia/Dubai`. Bucketing in UTC puts a 4am Dubai order on the
    previous day.

20.4  PHONE
  E.164 normalisation on write, UAE default region. `+971 50 214 8873`,
  `050 214 8873` and `971502148873` are one customer.

  entries. Do not "fix" this by reintroducing the settled flag.

24. BUILD ORDER
================================================================================
Each phase is releasable and unblocks the next.

  PHASE 0  TENANT FOUNDATION
    Tenant model, tenantContext middleware, the Mongoose isolation plugin,
    the isolation test suite, env config, error envelope, health checks.
    Nothing else starts until the plugin is proven.

  PHASE 1  IDENTITY
    OTP auth with a swappable provider, refresh rotation, staff and platform
    login, roles and the permission matrix, /config, tenant onboarding.
    Why first: every module needs a trustworthy caller and a place to read
    fees and flags from.

  PHASE 2  CATALOG AND MEDIA
    Categories, products, variant matrix, stock flags, upload, search tokens,
    Excel import. Ship api/catalog.ts in the app against the existing client
    wrapper.
    Why here: turns five app screens from static to live. The biggest lift.

  PHASE 3  PRICING AND ORDERS
    Pricing engine, promo validation, order creation with server-issued
    reference and confirmation code, both status chains, rider assignment,
    idempotency.
    Why here: closes all four CMS-SCOPE security blockers.

  PHASE 4  CUSTOMERS, ADDRESSES, CREDIT
    Address book with the primary invariant, credit approval, the ledger,
    statements, overdue reporting.
    Why here: the ledger is written from real orders, so orders come first.

  PHASE 5  DELIVERY STAFF AND CURBSIDE
    Delivery app endpoints, proof of delivery, availability, arrival queue,
    bays, car profiles.
    Why here: improves an experience that already works end to end.

  PHASE 6  REALTIME, NOTIFICATIONS, MERCHANDISING
    Socket.io, Expo push, banners, popular and trending, legal pages,
    translation strings.

  PHASE 7  ANALYTICS AND PLATFORM
    Rollups, the Insights endpoints, RFM, super admin portal, plans,
    invoicing.
    Why last: analytics need real traffic to be worth anything, and billing
    needs tenants who have been live long enough to bill.
